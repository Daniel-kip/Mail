1Executive summary

Mailvora is a self-hosted, multi-tenant business email platform for Kenyan institutions and developers. It relays transactional email for applications through a REST API, hosts work mailboxes on an organisation's own domain, and bills flat monthly prices in Kenyan shillings through M-Pesa.

1 VPSDocker Compose deployment, no git required
8services: Nginx, web app, API, PostgreSQL, Postfix, Dovecot, Rspamd, Redis
7public ports: 22, 25, 80, 443, 465, 587, 993
KESflat pricing; M-Pesa STK push via PesaTide

Purpose and scope

This document describes how the platform is built and how data and trust move through it. It is the reference for operators deploying and running Mailvora, for security reviewers and penetration testers, and for engineers changing the system. It covers the production topology defined in backend/docker-compose.yml and the host Nginx site in backend/infra/nginx/mailvora.conf.

Architecture principles

  • Proven mail software for protocols. Postfix handles SMTP, Dovecot handles IMAP, LMTP, SASL, Sieve and quotas, and Rspamd filters spam. Mailvora's Rust service is the control plane and never implements SMTP or IMAP itself.
  • Backend-for-frontend. Browsers talk only to the PHP web application; it calls the Rust API over a private address and keeps API session cookies server-side.
  • Tenant isolation by construction. The organisation is always derived from the authenticated session or API key, never from request input, and every query is scoped by it.
  • Secure by default. Production refuses to start with unsafe settings (plain-HTTP addresses, insecure cookies, debug output, development shortcuts).
  • Durable, idempotent processing. Messages and jobs are stored before they are acknowledged; workers claim jobs with leases, retry with back-off and never send twice for the same idempotency key.

5.2 Inbound mail and mailbox access

Web request flow (browser → web application → API)

  1. The browser connects to app.example.com over TLS; Nginx applies rate limits and forwards to the web application on loopback.
  2. The web application starts the session, opens any sealed /app?ref=… link with the session's key, and routes the real path.
  3. CSRF, authentication and permission middleware run; the controller calls the API at its private address, presenting the API session cookie kept in the PHP session (never in the browser).
  4. The response is rendered; every private address in it is sealed before it is sent, and secrets are shown once.

6.1 Security flow of a browser request

What a refused request receives

LayerResponse
Rate limit exceeded429 Too many requests with a plain message; nothing about the account is revealed.
Sealed link edited or expiredRedirect to the area's home with "That link has expired or was changed"; a typed record address is refused the same way; a direct form post gets 404.

6.2 Trust boundaries

IDBoundaryControls at the crossing
TB1Internet → edge and mail tierFirewall allow-list; TLS 1.2+ everywhere; HSTS; per-IP rate limits; Postfix recipient validation and relay restrictions; Rspamd scoring; Dovecot TLS-only authentication.
TB2Edge → applicationLoopback-only listeners; internal API paths blocked at Nginx; CSP, CSRF, sessions, sealed links, input validation; API keys and sessions verified on every call.
TB3Application → dataSeparate database roles (migrations, runtime, read-only mail servers); parameterised SQL; tenant scoping; secrets encrypted with AES-256-GCM; tokens and codes hashed; backups encrypted.
TB4Mail tier ↔ applicationPlatform relay only for the authenticated relay identity; auto-reply listener only from the private network; bounce ingestion requires the internal API token; mail servers read the database through a read-only role.
TB5Application ↔ third partiesOutbound: SSRF-guarded client (public addresses only, no redirects, DNS-rebinding safe). Inbound: PesaTide webhooks verified by HMAC-SHA256; Google ID tokens validated; credentials only in stack.env.

6.3 Defence in depth

6.4 Tenant isolation

Every organisation-owned row carries its organisation identifier, enforced by composite foreign keys. The API derives the organisation from the authenticated session or API key and adds it to every query; request bodies and URLs never choose the tenant. Mailbox users are confined to their own mailbox, and the webmail session cannot call console endpoints. Integration tests attempt cross-tenant access for every resource type and must receive "not found".

Kenya Data Protection Act, 2019

  • The privacy notice lists every processor (PesaTide, Africa's Talking, Google sign-in, Pwned Passwords) and the right to complain to the Office of the Data Protection Commissioner (ODPC).
  • Institutions are data controllers for their staff's mail; Mailvora acts as their processor. The operator should register with the ODPC before launch.
  • Data subject requests (access, correction, deletion) are handled by operators from the operator console and the database, and recorded in the audit log.

Backups

backend/infra/scripts/backup.sh runs daily from cron. It dumps the database (pg_dump -Fc), archives the mailboxes and the configuration, writes SHA-256 checksums, encrypts everything into one archive with GnuPG (AES-256, passphrase file chmod 600), prunes archives older than the retention period, and is copied off the server to a different provider. A restore is drilled on a scratch VPS every quarter.

9Operations

Monitoring

  • /healthz on the web app reports web and API health.
  • API metrics: outbox depth and oldest pending age, messages and webhook deliveries per hour, suspended organisations, database pool usage.
  • Operator console: delivery queue and failed jobs, receivables, security overview (failed sign-ins, locked accounts, operators and owners without MFA, privileged activity).
  • Container health checks and automatic restarts; bounded JSON logs.

Incident response

  • Compromised tenant: suspend the organisation (revokes sessions, keys and mail access immediately), review the audit log, notify the owner.
  • Spam outbreak: suspend the sender, inspect the queue, requeue or drop jobs, check blocklists with the deliverability tools.
  • Payment dispute: reconcile with PesaTide by reference and receipt; operators can record or void invoices.
  • Host compromise: rebuild from a clean image, restore the latest verified backup, rotate every secret in stack.env.
